**Goal (dev, 2026-11-25):** "a mode where you do not need to sign in at all, and all of the networking that goes into it can be disabled", like StrideRush, without a second copy of the game rules ("that would mean basically creating a clone of the game"). The server program stays exactly as it is for local-online testing and the VPS. Players get only the client; no cfs.exe, no hosting.

**Approach:** the client loads the server's own code as a second script module ([[offline-module-poc]] proved it, script and compiled) and connects to it through an in-memory bridge instead of enet. The server code still thinks a client connected; the client still thinks it reached a server. So the lobby, rooms, games, bots, walls and menus all run from the same code as online.

**Key finding (2026-11-25):** both sides touch the network only through `network net;` and `network_event event;`:
- server: `net.setup_server`, `net.request` (3 places), `net.send_reliable` / `net.send_unreliable` (netfuncts.nvgt), `net.disconnect_peer_forcefully` / `net.disconnect_peer_softly`, `net.IPV6enabled`.
- client: `net.setup_client`, `net.connect` (2), `net.request` (6), the two sends (netfuncts.nvgt), `net.disconnect_peer_forcefully` (11), `net.IPV6enabled`.
- The engine's `network_event` fields are `const` (network.cpp 277-280), so script can't build a fake one. Hence a script wrapper class with the same field names.
- The engine also has `setup_local_server`, but that is still networking; not used.

**Requirements from the PoC:** join the server's include tree into one text with its own deps; `set_access_mask(0xFFFFFFFF)`; `reset_globals()` after build (and again to reset); messages as the same text strings; data paths resolve against the client's cwd (cf/client), where data/config already mirrors the server's.

**Sections (final, Q&A complete 2026-11-25; build in this order, each tested before the next):**

1. **Network wrapper (client and server).** Each side gets a small script class with the same method names (`setup_server`/`setup_client`, `connect`, `request`, `send_reliable`, `send_unreliable`, `disconnect_peer_forcefully`/`softly`, `IPV6enabled`) and an event class with the same field names (`type`, `peer_id`, `channel`, `message`). `network net;` becomes the wrapper; `network_event event;` becomes the wrapper's event type. Online, every call forwards to the real enet object, so behavior is identical; offline, calls go to the bridge. Encryption stays as it is. Nothing offline exists yet, so the test is purely: online play unchanged, client and server. **DONE 2026-11-25:** new `includes/main/deps/game_network.nvgt`, byte-identical on both sides (classes `game_network`, wrapping `network real`, and `game_network_event`; IPV6enabled as a get/set property; request() copies the engine event's four fields into a fresh game_network_event, event_none when nothing waits). In each side's `globals/net.nvgt` only the two declarations changed: `network net;` to `game_network net;` and `network_event event;` to `game_network_event event;`. No other code changed: every net. call (setup, connect, request, the two sends, both disconnects, IPV6enabled) already matches a wrapper method, and nothing else names the engine types. downcheck.nvgt has no network code.
   - **First launch failed (2026-11-25) on both sides:** "Found multiple matching enum values" at game_network.nvgt line 12, `int type = event_none;`. form.nvgt's own enum also has an `event_none = 0`, so the bare name is ambiguous. Fix: the field is now `network_event_type type = network_event_type::event_none;`, which also keeps every existing `event.type == event_receive` comparison resolving exactly as with the engine event. At the dev's request Claude compile-checked both sides once (`nvgt -c` in src/server and src/client, no server started): both "Release build succeeded"; the two output folders were deleted afterwards. Tested online by the dev 2026-11-25: "both client and server works". Section 1 COMPLETE.

2. **Server startup split and host path (server).** cfs.nvgt's main() becomes `server_init()` (the current setup) + `server_tick()` (one pass of the netloop/gametick loop), with main() calling them as today. Guard what only makes sense as a real program, so an offline game can never close or restart the client: the single-instance check, the server window (`show_game_window`/`hide_window`), `exit()` and relaunch in /restart and /shutdown. The ~60 `data/host/` paths read one variable (`data/host/` online; the saves folder offline, see Q&A), so online is unchanged. Test: the server runs exactly as before.

3. **Offline behavior inside the server code (server).** All behind an offline flag the client sets: sign-in without a password (the profile is created directly, so the 6-24 username rule is checked by the client's prompt instead); the hidden private room; the start-game cascade minus PVP and the solo/open and player-limit steps (always solo); the agreed left-out features refused or never offered (Q&A); and a game's end sending the player back to the client's game menu instead of the room. Test: online unchanged (the flag is off).

4. **Offline loader and bridge (client).** New client file: get the server code (the section 6 constant, or join `../../src/server` live when that constant is empty), build the module with the PoC's three requirements (own deps, `set_access_mask(0xFFFFFFFF)`, `reset_globals()`), bind the bridge, set the offline flag and the saves path, call server_init, then each frame pump server_tick and deliver queued messages both ways. Compile once per launch; each later offline game resets with reset_globals(). Profile saved on leaving.

5. **Menus and name prompt (client).** Main menu loses "learn sounds menu"; game menu becomes play game, learn sounds, back; play game opens "Choose how you'd like to play." with online, offline, back; online opens the existing online menu; offline asks the name the first time (saved in settings.cvf; an existing saves profile is adopted after a settings reset), then starts the offline session. Escape steps back silently; a finished or left game returns to the game menu. Test: full offline play, plus online unchanged.

6. **Build tools (build).** tools.py writes the joined, single-line-escaped server code into `src/client/includes/scripts/server.nvgt` as `offline_server_code`, compiles the client, and always restores the empty placeholder (finally block). The placeholder and the `#include"scripts/*"` line are committed in this section. Nothing else of the server ships with the client.

7. **Docks (docks).** Readme: an offline play section, the client's own data/config copy (deferred here from [[data-reorg-repointing]]), and the moved learn sounds (main-menu line 7 and the Learn sounds section). Changelog: one 5.3 entry for offline play plus a rewrite of the 5.3 online-menu entry for the new menus. Memories: [[path-conventions]], [[include-tree]], [[launchers-and-running]], [[networking-protocol]], [[online-menu]], [[learn-sounds-menu]]; mark this plan COMPLETE.

- Q (superseding the scripts-folder answer above): the dev then moved scripts/ to %APPDATA%\tsatria03\CaveDefender\scripts; Claude explained a portable 7z can't put files in appdata and a stale copy there would mismatch an updated client. The dev's real concern (2026-11-25): "I was hoping players did not see the code at all because it risks them deleting it, and then the offline menu would be broken." So:
  - The server code travels INSIDE cfc.exe; no loose file anywhere, so neither cf/client/scripts nor appdata/scripts is needed.
  - Committed placeholder: **src/client/includes/scripts/server.nvgt**, holding `const string offline_server_code = "";`, included by a new `#include"scripts/*"` line in includes.nvgt (the client's glob style).
