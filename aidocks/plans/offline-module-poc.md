**Why:** the dev wants an offline mode like StrideRush: no sign-in, no server program, no networking, and no second copy of the game rules (dev, 2026-11-25: "I really hope not because that would mean basically creating a clone of the game"). The server and its local-online/VPS use stay exactly as they are. Option A (dev chose it 2026-11-25, "I like option A better"): in offline mode the client loads the server's gameplay code as a second script module and passes messages by direct calls instead of enet. Option B, a shared src/shared game-rules folder included by both sides, is the fallback if this proof of concept fails. Users would not get the server program (cfs.exe), accounts or hosting; only the gameplay code inside the client, reading the client's own data/config copy (same paths as the server's, so no path changes; see [[data-reorg-repointing]]).

**Engine facts (checked in the Legacy-NVGT source, 2026-11-25):**
- scriptstuff.cpp registers `script_module` (`script_get_module(name, mode)`, `add_section(name, code)`, `build(errors)`, `get_function_by_name/decl`, `get_bytecode`/`set_bytecode`, `compile_function`, `discard`, imported-function binding) and `script_function` (`call(dictionary args, string[] errors)`: arguments go in the dictionary under keys "1", "2", ...).
- The main script's module is named "nvgt_game" (nvgt_angelscript.cpp).
- Compiled games keep the compiler: the stub is `nvgt_windows.bin` unless a script says `#pragma stub nc` (bundling.cpp 155), and CaveDefender has no such pragma. `nvgt_windows_nc.bin` (no compiler) exists in C:\nvgt\stub but is unused. If runtime compiling ever failed, `get_bytecode`/`set_bytecode` (build once, ship bytecode) is the backup.
- `add_section` takes plain code text: it does NOT follow `#include`. The real offline mode would need the server's include tree joined into one text at build time (the PoC tests a small joiner).

**What the PoC must prove (each a pass/fail line in the results file):**
1. Load: read a test module's source, `add_section` + `build` succeed, and compile errors are captured into a string array (not lost).
2. Call in: the host calls a module function with a string argument (`dictionary` key "1") and reads its return value.
3. Call back out: the module hands messages back. Test both ways: (a) polling, the host calls a module function that returns the queued messages; (b) an `import ... from "nvgt_game"` function bound with `bind_all_imported_functions`, so the module calls the host directly.
4. Isolation: the host and the module each define a function `send(...)` and a global `players` with different meanings; both build and each uses its own.
5. Engine features inside the module: `file` reads `data/config/main/modes.ini` relative to cwd, and a `timer` runs.
6. Include joining: two small module files where one `#include`s the other, joined into one text by a tiny joiner in the host script, then built.
7. Speed: 10,000 round-trip calls, timed, to see the cost per message (gameplay sends a few hundred a second at most).
8. Compiled: the same test compiled into an exe gives the same results, proving release builds keep runtime compiling.

**Result: Option A works.** Requirements the real offline mode must meet, all learned here:
1. Join the server's include tree into one text (add_section does not follow #include), carrying its own `main/deps` (bgt_compat etc.), since a module never sees the host's script helpers. `shared` functions in bgt_compat are fine on both sides.
2. `set_access_mask(0xFFFFFFFF)` before building (a new module starts sandboxed: pack_file and friends are hidden).
3. `reset_globals()` after building (NVGT disables automatic global setup; skipping it crashes silently on the first global touched). Calling it again resets the offline game.
4. Messages can travel as the same text strings the server sends today: about 0.01 ms each, either polled or through an `import ... from "nvgt_game"` callback.
5. Data files resolve against the client's cwd, so the client's data/config copy works with the server code's existing paths.
